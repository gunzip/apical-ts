# Hono Route-Metadata Template

This example shows the **dynamic, metadata-driven** integration style and is now
meant to be **forked and reused locally**. Apical TS first generates route
metadata, then a second local generator turns that metadata into a Hono layer.
The API contract stays the same; only the framework integration changes.

By default the Hono generator creates **one userland handler file per
operation**. Each handler gets:

- `input`: validated params, query, headers, and body extracted from the route
- `context`: the Hono context for that route

The handler return type is also **strictly constrained** to the route response
union generated by Apical, so userland code cannot return arbitrary status
codes, content types, or payload shapes.

Mock handlers remain a separate, optional demo step.

## Contract-first flow

1. Put your contract in `openapi.yaml`.
2. `pnpm run generate:routes` runs Apical with `--routes`.
3. Apical emits `generated/routes/*` plus the shared schemas and package files.
4. `pnpm run generate:hono` reads those route files and produces
   `generated/hono/*` plus one non-generated handler stub per operation under
   `handlers/*`.
5. `registerGeneratedRoutes(app)` mounts the generated routes, and each route
   imports its own handler file.
6. `pnpm run generate:mocks` is optional and swaps the handler source to
   generated demo-only mock handlers backed by `zocker`.

## Why this is the dynamic style

- **Express** wires each route explicitly with generated wrappers.
- **Hono in this folder** derives the framework layer from generated route
  metadata instead of registering routes one by one.
- The contract is still modeled once, so moving from Express to Hono does not
  require reshaping handlers, payloads, or status unions by hand.

## Quick start

1. Fork the repository and install dependencies from the monorepo root:

   ```bash
   pnpm install
   ```

2. Move into the example:

   ```bash
   cd examples/hono
   ```

3. Replace `openapi.yaml` with your contract and generate the reusable Hono
   layer:

   ```bash
   pnpm run generate
   ```

4. Implement the generated handler stubs under `handlers/*`.

If you want the demo mock server too, run:

```bash
pnpm run dev
```

The demo server runs on `http://localhost:3002`.

## Handler contract

Each generated operation module exports its own handler type, and each route
imports a handler file with the same basename.

Example `handlers/addPet.ts`:

```ts
import type { AddPetHandler } from "../generated/hono/operations/addPet.js";

export const addPetHandler: AddPetHandler = async (input, _context) => {
  return {
    status: "200",
    contentType: "application/json",
    data: input.body,
  };
};
```

`AddPetHandler` only accepts responses that belong to the generated
`addPetRouteResponse` union for that route.

All request-derived values should come from `input`, where `path`, `query`,
`headers`, and `body` have already been validated against the generated route
schemas. Use `context` only for Hono runtime concerns that are not part of the
validated request payload.

Then your server only needs:

```ts
import { Hono } from "hono";

import { registerGeneratedRoutes } from "./generated/hono/register-routes.js";

const app = new Hono();
registerGeneratedRoutes(app);
```

This keeps all userland code outside `generated/hono/*`, and the generator does
not overwrite existing handler files when rerun.

## Customizing input and output

The second step stays explicit and accepts custom paths:

```bash
pnpm run generate:hono -- --routes ./generated/routes --output ./src/generated/hono --handlers ./src/handlers
```

To generate the optional mock layer on top of the same routes:

```bash
pnpm run generate:mocks -- --routes ./generated/routes --output ./src/generated/hono
```

## Project layout

- `openapi.yaml`: local contract to replace when you fork the example
- `handlers/*`: userland handler stubs generated once, then owned by you
- `generated/routes/*`: route metadata generated directly by Apical
- `scripts/generate-hono-server.ts`: CLI entry point for the second-step
  generator
- `scripts/hono-generator/*`: Hono-specific code generation utilities
- `generated/hono/operations/*`: generated Hono route modules
- `generated/hono/register-routes.ts`: generated route registration entry point
- `generated/hono/runtime.ts`: shared runtime helpers for the standard flow
- `generated/hono/handlers/*`: optional mock handler files for the demo flow
- `generated/hono/mock-runtime.ts`: optional mock runtime backed by `zocker`
- `server-examples/mock-server-example.ts`: runnable demo server using the
  optional mock layer

## Example prompt

If you want to recreate this integration from scratch starting from the OpenAPI
contract, you can use a prompt like this:

```text
Goal: build type safe Hono handlers by first generating route metadata with @apical-ts/craft and
then writing a generator that emits the Hono integration.

Process:
1. Run `npx @apical-ts/craft generate --routes -i openapi.yaml -o generated`.
2. Inspect `generated/routes/*` and use them as the only source of truth for
   `operationId`, `path`, `method`, `params`, `requestMap`, and `responseMap`.
3. Implement the generator entrypoint in `scripts/generate-hono-server.ts`.
4. Implement the generator modules under `scripts/hono-generator/*` so they read
   generated route metadata and emit `generated/hono/*`.
5. The generator should produce:
   - one generated Hono operation module per route
   - one handler file per operation for userland code
   - a register-routes module that mounts routes without a central handlers object
   - shared runtime helpers
   - an optional mock layer for demos, not for the default flow
6. Add a runnable Hono server that imports the generated registration layer.

Rules:
- do not hand-write `generated/hono/*`
- do not redefine endpoints or payload types outside @apical-ts/craft output
- request validation must be driven by generated schemas and metadata
- use `@hono/zod-validator` where request validation is needed
```
